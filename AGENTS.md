# Repository Guidelines

This remote is public, so this file describes the project and nothing else. Anything tied to the machine it is worked on — attached devices, paths outside the repository, where unpublishable material is kept — belongs in `AGENTS.local.md`, which is git-ignored. **Read it first if it exists**, and when something turns out to be local rather than general, write it there instead of here.

## Project Structure & Module Organization

Design decisions that are easy to mistake for accidents are collected under **Deliberate choices** at the end of this file; keep that list current, because everything else here assumes them.

Paperouette is a single-module Android 17 live-wallpaper app. Kotlin sources are under `app/src/main/java/dev/paperouette/wallpaper/`, grouped into `data`, `model`, `motion`, `render`, `ui`, and `wallpaper`. Android resources live in `app/src/main/res/`. The normalized catalogue and its checksums are in `app/src/main/assets/catalog/` and are tracked; the content-addressed artwork they describe is in `app/src/main/assets/artwork/` and is **not** — it is generated, git-ignored, and rebuilt by `uv run tools/generate_catalog.py`. Nothing here uses Git LFS.

Local JVM tests belong in `app/src/test/`. Device, Compose, DataStore, and OpenGL tests belong in `app/src/androidTest/`; the reference frames `SceneRendererTest` compares against are generated and git-ignored too, so a fresh clone needs `uv run tools/generate_catalog.py --fixtures app/src/androidTest/assets/previews` before it can run them. Maintenance scripts are in `tools/`, CI is in `.github/`, and release instructions are in `docs/INSTALL.md`.

## Architecture

Two render hosts share one renderer:

- `render/SceneRenderer` is a pure GLES3 layer/filter renderer. It caches textures by asset path across scene switches, decodes with a viewport-derived `inSampleSize` budget, and generates mipmaps. A failed scene load must leave the previous scene fully renderable (tested). Blur renders through two quarter-res framebuffers; dim and grayscale are shader uniforms. The layer shader discards outside a layer's rectangle, so framing decides whether a rotation exposes an edge — see `SceneCoverage` below.
- The scene turns about a **centre of rotation** placed anywhere on the screen, `PaperouetteSettings.rotationCenterX/Y`, as a fraction of the viewport from its top left. The artwork's middle is drawn at that spot and the rotation happens around it — the point moves, the middle of the glass does not stay the pivot. The shader takes it as `uPivot`; the setting measures down from the top the way a touch does, while `vUv` measures up from the bottom, so the renderer uploads `1 - y`.
- `SceneCoverage`, in `render/RenderModels.kt`, frames the scene. The artwork is square (2048×2048, uniformly — see `tools/catalog/`) and is sampled through a viewport-shaped window, whose corners sweep a circle as the scene turns; unless the window is shrunk to the artwork's inscribed circle, a rotating opaque layer shows its edges. `SceneCoverage.window` cover-fits, then shrinks when the **base** layer rotates, reserving `LayerTransform.maxParallaxOffset` of pan headroom. The shrink follows the viewport's shape, not its resolution — roughly 17% on a tall phone, more as the screen approaches square. Layers above the base are drawn on transparent surrounds, so their corners leaving the image is invisible; framing the whole scene by the base layer's need keeps every layer registered with the others. Scenes whose base layer is static are framed exactly as cover-fit.
- `render/EglRenderHost` owns the "PaperouetteGL" HandlerThread, the EGL context and surface, frame scheduling, EGL failure recovery, and hidden-surface memory trimming. All GL work happens on that thread; public methods post to it. **Nothing waits for it.** `release` and `detachSurface` take completion callbacks that run on the GL thread rather than blocking the caller — they used to await a latch, and since the GL thread can be a second deep in decoding a scene's layers, that stalled the main thread for over a second every time the preview scrolled off screen. For the same reason `PaperouettePreviewView.onSurfaceTextureDestroyed` returns **false**, keeping the `SurfaceTexture` ours to release once EGL has finished with it.
- Detaching the surface keeps the renderer's textures, because they belong to the EGL context rather than the window. A detached host schedules the existing `HIDDEN_TRIM_DELAY_MS` trim, which drops the whole context when there is no surface to make current — measured to return about 40 MB of graphics memory. So scrolling the preview away and back is cheap, while leaving it away still reclaims everything.
- The preview `PaperouettePreviewView` is created and released in `CatalogueScreen`, **not** inside the grid item that draws it. A `LazyVerticalGrid` disposes what scrolls out of it, and disposing the view rebuilds a thread, an EGL context and every decoded layer on the way back. `onDetachedFromWindow` therefore only stops rendering; it must not release. `FramePacer` paces 60 fps during interaction and 30 fps idle on absolute deadlines; `AnimationClock` freezes the animation timeline while hidden or battery-paused.
- The hosts are `wallpaper/PaperouetteWallpaperService.PaperouetteEngine` (system wallpaper) and `ui/PaperouettePreviewView` (TextureView preview inside Compose via `AndroidView`). Each has its own `MotionController` and `EglRenderHost`.
- `PaperouetteEngine.isBatteryPaused` must not depend on `visible`, and neither must anything else that goes into a `RenderFrameState`. It used to, which made the state pushed to the renderer depend on *when* it was computed: `onVisibilityChanged` does not recompute it, so a wallpaper that became visible with the saver already on carried a stale `animationPaused = false` and kept turning at 30 fps while its sensors were stopped — corrected only by the next settings emission, or by a power broadcast that had already fired. Visibility gates the rendering one layer down, in `EglRenderHost`, which advances the clock only while `visible && !animationPaused`.
- `MainActivity` uses `fullUser`, so it follows the user's rotation lock and admits portrait, landscape and both reverse orientations when rotation is enabled. It declares `configChanges` for orientation, size, density and `uiMode`; without that every rotation destroyed the activity, and disposing `PaperouettePreviewView` rebuilds a thread, an EGL context and every decoded 2600×2600 layer. Compose still sees the new `Configuration`, so `isSystemInDarkTheme` and the automatic dark variants keep following the system.

Supporting layers:

- **Only two renderings of each variant ship**: its layers, and one 260-square thumb, so `PreviewAssets` is a single required `thumb`. The layers are **not** oversized and must not be shrunk: on a 1280x2856 screen the visible window samples roughly 0.37 x 0.83 of the square artwork, so it is already being upscaled.
- **A layer is a resolved picture.** The renderers in `tools/artwork/` shade, light and composite in ways a single ramp lookup cannot express, so every layer ships as resolved colour, carries no `ramp`, and each variant — including its dark twin, which is the same render held down by `NIGHT_DIM` — has its own pixels. The renderer's ramp path still exists (`SceneRenderer` uploads a 256x1 premultiplied lookup when a layer has one, and draws the texture as-is when it does not), but the bundled catalogue no longer uses it, and `CatalogSchemaTest.everyLayerShipsResolvedColour` holds that line. The costs are real and accepted: colour variants share no image files, so the APK carries an image per layer per colour variant — only effect variants share canonical layers, by content address — and a switch between colour variants has no shared textures to keep warm.
- `SceneRendererTest`'s SSIM references live in `app/src/androidTest/assets/previews/` and ship with the test APK; the test reads them through the instrumentation context, not the app's. Regenerate them with `uv run tools/generate_catalog.py --fixtures app/src/androidTest/assets/previews`. Because they come out of the same maths that draws the artwork, agreement should be close; the current limits still owe a device run the tightening-to-measured-headroom pass. Tighten them then — and never loosen one to make a change pass.
- **The catalogue is a snapshot, not a constant.** `data/CatalogSnapshot` is an immutable value — designs, remixes and their lookups together — and `CatalogRepository` exposes a `StateFlow` of one. It became a value when artwork became importable: a composition and the GL thread must not be able to read the design list from one moment and the remix map from the next. Callers pin one snapshot and work from it; `PaperouetteApp` collects it, so the collection redraws when an import lands or goes. `PaperouetteCatalogRepository` composes the bundled snapshot with the imports, **bundled first** — `nextDesign` and `shuffle` index into these lists and the default selection is looked up in them, so putting imports in front would move all of that under the user's feet every time one was added.
- `data/ArtworkPaths` turns a catalogue path into an `ImageSource` saying which store holds the bytes: `assets/…` is the APK, `imported/…` is app-private storage. It is a pure function of the prefix, which is why the renderer, its EGL host and `SceneTone` need no catalogue at all — only to be handed a `Remix`.
- `data/ArtworkImporter` brings artwork in from the phone, on the application scope rather than behind a ViewModel: a 180 MiB copy has to outlive the sheet being dismissed and the user going home. It reads one bounded pass over an `ImportSource` — the seam the picker's `Uri` stops at, so the pipeline is testable without a `ContentProvider` the release check would refuse — and decides what it has from the first entry: `paperouette-pack.json` means a pack, anything else means pictures. A pack's content-derived identity, counts, relationships and exact catalogue bytes are checked before staging is created; pictures, metadata and assets are streamed to fixed limits. Starts use `Mutex.tryLock`, so a second picker result is closed rather than queued, and cancelling closes the active source before cleaning staging. `data/ImportStore` owns the on-disk layout, resolves every id canonically under its root, and treats an import as existing exactly when its directory holds a matching manifest that parses; the whole directory is renamed into place in one step, so there is no index to fall out of step with the filesystem and a crash leaves debris to sweep rather than a dangling reference to chase.
- `data/BundledCatalogRepository` parses the bundled catalogue once (warmed off the main thread in `PaperouetteApplication.onCreate`) and hard-fails on unexpected counts, remote URLs, or an `inputRotationScaler` incompatible with the spin wrap period.
- `data/DataStoreSettingsRepository` exposes `settings` and `selection` as eagerly shared StateFlows. Invariant: selection mutations (`selectForDarkMode`, `nextRemix`, `nextDesign`, `shuffle`) read preferences via `safeData.first()`, never via `StateFlow.value` — the caches hold defaults until the first disk read and acting on them can clobber the user's saved selection. Write failures are swallowed by design; the offline app keeps its last valid in-memory state.
- Selection semantics, learned from two bugs a year apart. **`isDark` is a measurement, not a pairing.** It records how dark a render came out — `generate_catalog.py` compares the thumb's tone to `DARK_TONE_CROSSOVER` — so it says nothing about which half of a pair a remix is. All twelve of Pocket Planetarium's remixes measure dark, `Golden Hour` and `Golden Hour (Dark)` alike. **Theme twins pair by label only**, `Moss` / `Moss (Dark)`, which is what `twinFor` looks for. Not by id either: the generator writes `_dark` on both halves it makes itself, but Spinner 32's `Blue` and `Blue (Dark)` are `_color_1` and `_color_2`, so an id rule misses all seven of its pairs. Only 158 of the 352 remixes are in a pair at all — the twelve layered designs and Spinner 32 — and seven designs have no pair whatever. `CatalogSchemaTest.everyDarkLabelIsPairedWithExactlyOneBaseInItsOwnDesign` holds the invariants that rule needs. So:
  1. `selectDesign` anchors on the design's own `previewRemixId` — the artwork on the tile the user tapped — and swaps it only for a label-paired twin. Treating "first dark remix" as a design's dark form is what made tapping Rainbow Whirlpool produce Dot Bomb.
  2. **An explicit pick outranks the theme.** `selectForDarkMode` follows the system theme and *only a change of it*: the theme a selection was resolved against is recorded in `selection_resolved_dark`, and nothing happens until the system disagrees with that record. It used to re-resolve on every call, and its callers are every launch and every `onVisibilityChanged(true)`, so a variant picked by hand lasted until the next visit to the home screen — the whole variant strip looked broken on a light-themed phone. An absent record means an upgrade, which keeps what it has.
  3. **A theme change never falls back to the preview.** It takes the user's own pick for the new theme, else the twin of what is *showing* (not of the preview — from `Slate` the dark form is `Slate (Dark)`), else leaves the selection alone. With 194 remixes having no twin, reaching for the design's tile artwork throws the choice away and gives nothing back.
  4. Browsing with `nextRemix` covers every remix of the design rather than filtering by theme, which would jump from a light remix straight to an unrelated dark one.
  5. Only remixes the user actually picked enter the remembered-variants map, because recording the app's own fallback as a choice let a wrong resolution outlive the fix that corrected it. The map is keyed by **the theme in force when the pick was made**, not by the tone of the artwork picked — keying by tone put every pick on a light-themed phone into the dark drawer and left the light one empty. It carries `REMEMBERED_VERSION` (now 5); bump it whenever stored entries can no longer be trusted, and older entries are discarded on read.
  6. **A change the app made on a timer is not a pick either.** `shuffleIfDue` activates with `remember = false`, so the map keeps whatever the hand last chose and tapping the piece still brings it back. It does write `selection_resolved_dark`, as every activation does, or the next `selectForDarkMode` would undo it.
- `motion/MotionController` handles sensor and touch input with synchronized methods; the GL thread samples it per frame via `snapshot()`, which also advances inertia physics. Spin wraps over 4 whole turns (`MotionMath.SPIN_WRAP_TURNS`); the renderer multiplies spin by each scene's `inputRotationScaler`, so the wrap period times the scaler must stay a whole number of turns (checked at catalogue load). Spin reaches only layers the catalogue gives a `rotation` spec — turning a scene's static full-bleed backdrop would swing its edges into view. `LayerTransform.parallax` bounds the combined launcher, drag and tilt input to a unit per axis so panning stays inside the headroom `SceneCoverage` reserves.
- Gestures: one-finger drag is parallax, a two-finger tap selects the next remix, a three-finger tap selects the next design. Multi-finger gestures deliberately disable dragging for the rest of the gesture.

Interface, in `ui/`:

- The app **is** the wallpaper. `ui/LiveStage` draws `PaperouettePreviewView` at full window size as the ground the whole interface stands on; there are no destinations and no preview card. That means the renderer's own gestures reach the entire screen, and a filter set in the app looks exactly as it will on a wallpaper surface of the same shape. The view is created and released in `PaperouetteApp` itself, so it never leaves composition while the app is open.
- `ui/CollectionSheet` supplies everything the sheet holds. At rest it shows the piece and variant on the stage, the heart, shuffle, **Set wallpaper**, the two panel buttons and the variant strip; pulled up it becomes the collection. `SHEET_PEEK_CONTENT_HEIGHT` is the sum of those parts and must stay equal to what `SheetPeekContent` actually draws — a few dp over and the collection's first row shows above the fold, a few under and the strip is clipped. Favourites is a filter on that collection, not a place of its own.
- **Play** is the sheet being gone: `PaperouetteApp` keeps a `playing` flag and the sheet's `SheetValue.Hidden` in step in both directions, so the button on the stage drives the sheet away and dragging the sheet away starts play. That is why the sheet is created with `skipHiddenState = false`. While playing the system bars are hidden too and the only way out is Back, since a tap on the stage belongs to the artwork — with Nudge on it is what sets the thing spinning. The wide layout has no sheet to push away, so it simply stops composing the side panel; the stage is in the same place in the tree either way, which is what keeps the `AndroidView` from being torn down and rebuilt.
- Two panels sit over the stage. `ui/LookPanel` holds dim, greyscale, blur and the centre of rotation, judged against the full-size artwork behind it; its Centre tab takes the drags itself, above the `AndroidView`, so `MotionController` never sees them. While that panel is open the sheet's peek height goes to zero, taking it out from behind the panel rather than merely hiding it under one — which is what lets the panel be only as tall as its own controls, so a centre placed near the bottom of the stage stays in view. The crosshair and its readout are composed **after** the panel and so draw over it, as a backstop for the last strip; neither takes pointer input, so drags still reach the stage and the panel's controls stay tappable through them. Four arrows at the stage's edges nudge the centre a hundredth of the surface at a time, because a fingertip covers the very point it is placing. Holding one repeats — and the repeat steps from a value the arrow keeps itself, not from the setting, because the round trip out through DataStore and back is slower than the repeat and reading it each tick stands still. `ui/BehaviourPanel` holds the sensor preferences and covers everything, so the stage is told to stop animating while it is open. Its last row is the build's own version name — the app is installed over adb rather than from a store, so there is otherwise no way to tell which build is on a phone, and a debug build says so through the suffix. Both are drawn **opaque**: the sheet is still composed underneath, and even a few percent of translucency lets its buttons read through them.
- `ui/PaperouetteControls` is the control vocabulary — `PaperouetteFader`, `PaperouetteToggleRow`, the actions and chips. They are hand-drawn rather than Material's because they sit on moving artwork rather than on a page. Each carries the semantics its Material counterpart would; `PaperouetteFader` in particular takes the caller's modifier on its **track**, since that is the node that must hold both the test tag and `setProgress`.
- `ui/theme/ArtworkColorScheme.chassis` builds the interface palette: fixed near-black surfaces that hold still, with the artwork's colours used only for accents. It is the only scheme there is — an earlier `of`, which tinted every surface, was kept for reference until 1.0.19 and has gone; `everyRemixProducesLegibleChromeOnTheChassis` covers what replaced it. Tones step in HSL because `material-color-utilities` is not a dependency and material3's copy is internal — HSL lightness is not perceptual, so **nothing assumes a tone is legible**: foregrounds are picked by measured WCAG contrast and accents step away from the surface until they clear it. `ArtworkColorSchemeTest` enforces this over every remix; run it before touching the colour maths.
- `ui/theme/PaperouetteMotion` holds the animation specs. Material's own `MotionScheme` would be the right source, but in material3 1.4.0 it, `MaterialTheme.motionScheme` and even `ExperimentalMaterial3ExpressiveApi` are all `internal`, so the expressive components (`ShortNavigationBar`, `MaterialShapes`, `FloatingToolbar`) cannot be used from outside the library yet. Revisit when 1.5 stabilises.
- Layout is adaptive off one breakpoint: below 600 dp the collection is a `BottomSheetScaffold` over the stage; at or above it the same content overlays the end edge as a fixed-width column, because a wide window is short and a sheet would leave the stage a letterbox. The full-window stage stays in place underneath, the panel intercepts touches across its whole footprint, and both branches call the same content composables.
- Three traps. A `LazyVerticalGrid` measures cells at a **fixed** width, so `aspectRatio` and `widthIn` have no room to shrink anything until centred inside a `Box`. Components apply their own window insets: adding `statusBarsPadding()` or `navigationBarsPadding()` on top double-counts them. And the sheet's expanded position is its content's height, so the sheet content is given a bounded height rather than `fillMaxHeight()` — a full-height sheet puts the piece's name behind the status bar and leaves nothing of the stage in view.

## Build, Test, and Development Commands

Development needs JDK 17, `uv`, and an Android SDK holding `platforms;android-37.0`, `build-tools;37.0.0`, and `platform-tools`, installed through Google's current `cmdline-tools`. Gradle finds the SDK through `ANDROID_HOME` or a git-ignored `local.properties`. `flake.nix` is retained for a possible return to NixOS only; never set `android.aapt2FromMavenOverride`, which was a NixOS-specific workaround.

```sh
uv run tools/generate_catalog.py
./gradlew assembleDebug
```

The first command is not optional on a fresh clone — the artwork is not committed — but it is needed only once, and again when something under `tools/` changes. JVM tests and lint do not need it: they read only the two tracked manifests.

Enable the hooks once per clone with `git config core.hooksPath tools/hooks`. `tools/hooks/pre-push` runs `testDebugUnitTest lintDebug`, the same checks CI runs, early enough to be cheap; it is the only hook, because with no Git LFS there is nothing to delegate to. Skip the checks for one push with `PAPEROUETTE_SKIP_VERIFY=1`. Lint runs with `warningsAsErrors`, the report being clean today, so the bar is that it stays clean; the three version-staleness checks `lint.xml` silences are the deliberate exception.

Use `./gradlew testDebugUnitTest lintDebug` for JVM tests and lint. Run a single test class with `./gradlew testDebugUnitTest --tests "dev.paperouette.wallpaper.render.FramePacerTest"`. Run `./gradlew connectedDebugAndroidTest` with an unlocked Android 17 device visible to `adb devices`; it runs on **every** attached device, so set `ANDROID_SERIAL` to target one. Regenerate the catalogue with `uv run tools/generate_catalog.py`; it is deterministic, so `git diff --exit-code -- app/src/main/assets/catalog` afterwards is the check that it still reproduces. That works even though the images are not tracked: `checksums.json` carries the SHA-256 of all 948 of them, so a clean diff there accounts for every byte. It is a **same-machine** check only — numpy dispatches CPU-dependent SIMD kernels, so a different machine renders visually identical images (under 0.02% of pixels differing by more than a rounding step, on anti-aliasing boundaries) under about 70% different content addresses. Disabling AVX-512 locally moves roughly a tenth of the hashes on its own; worker count, by contrast, changes nothing. Do not add a byte-comparison gate to CI: it would fail permanently while nothing was wrong. CI instead re-runs `CatalogSchemaTest` and `ArtworkColorSchemeTest` against its own freshly rendered catalogue.

Dependency verification is strict (`gradle/verification-metadata.xml`); adding or bumping a dependency requires updating the metadata. Regenerate with `./gradlew --refresh-dependencies --write-verification-metadata sha256 <the full task set>` — without `--refresh-dependencies` the writer silently skips artifacts already in the Gradle cache, which is how the file came to be missing five entries that only a cold machine ever downloaded. It adds entries without removing any, so review the diff. The only real proof of completeness is a build against a throwaway `GRADLE_USER_HOME`.

Release builds require ignored signing credentials. Follow `docs/INSTALL.md`, then run `./gradlew assembleRelease` and `uv run tools/package_release.py`. On a tag matching `v<versionName>`, `.github/workflows/release.yml` does the same on CI from the keystore held in repository secrets and attaches the result to a GitHub release; it renders the catalogue from scratch rather than from cache, because a release is the one build people install.

`.github/workflows/ci.yml` splits the work in two: a `check` job that runs tests and lint straight from the checkout, and an `apk` job that renders the catalogue — cached on a hash of everything under `tools/` that can change what it renders — before assembling a debug APK. Both call `.github/install-android-sdk.sh`, which is where the API level lives for CI. Third-party actions are pinned by commit SHA, for the same reason dependency verification is strict.

## Coding Style & Naming Conventions

Use four-space indentation and standard Kotlin conventions: `PascalCase` for classes and composables, `camelCase` for functions and properties, and descriptive package names. Keep state immutable at repository and renderer boundaries. Prefer small lifecycle hosts around shared rendering logic. Use trailing commas in multiline Kotlin declarations.

Python scripts must include PEP 723 inline metadata and run through `uv`. Keep XML resource names lowercase with underscores. Run lint before committing.

## Testing Guidelines

Tests use JUnit 4, AndroidX Test, Espresso, and Compose UI Test. Name test classes after the subject, such as `SceneRendererTest`, and test methods after observable behavior. Add JVM tests for catalogue or transform logic and instrumentation tests for GL, DataStore, UI, or Android lifecycle behavior. Renderer changes should cover deterministic zero-motion output (SSIM against bundled previews in `SceneRendererTest`) and GL cleanup.

Two traps in the existing suites are worth knowing before changing them:

- `SceneRendererTest` crops each bundled preview by the same factor `SceneCoverage` applies before comparing. Skip that and the SSIM only measures the framing difference — it collapsed from 0.98 to −0.13 when the framing changed and the reference did not.
- `SceneCoverageTest` proves the geometry by brute force, sweeping 360 angles × 8 pan directions × 4 window corners across several screen shapes and every subset layout the catalogue uses. Prefer that shape of test to asserting a magic scale factor.

When fixing a bug that persisted state, seed the old state in the test rather than trusting a fresh install — `variantsRememberedByEarlierBuildsAreNotTrusted` exists because a correct fix still looked broken on an upgraded phone.

Two more worth knowing:

- `PaperouetteUiTest` drives the real installed app, whose DataStore outlives the process, so a rule ordered ahead of the compose rule puts the settings back to their defaults before the activity launches. Without it every method inherited whatever the last one left, and that is not merely untidy: a test asserting a fader reads 60% passed on the second run whether or not it moved the fader. Assert from the default rather than reading the state first.
- The Look panel scrolls, and on a landscape phone its Filters tab is taller than the stage. Tap its lower controls through `performScrollTo()`; a tap aimed at the middle of a node below the fold lands off the bottom of the screen and silently does nothing.

## Commit & Pull Request Guidelines

History uses brief imperative milestone subjects, for example `Add wallpaper renderer`. Keep each commit focused and avoid generated build output.

Commit each change as it lands and is verified, rather than at the end of a session. The alternating pattern here — a feature commit, then `Bump version to 1.0.N` — only works if a feature is one commit's worth. 1.0.19 broke that: two features, six fixes, the hooks and the cleanup arrived as a single commit because they had been left uncommitted together, and by then `PaperouetteWallpaperService` held three of them and `RenderModels` another three. Overlapping edits in one file cannot be split afterwards without hand-built partial patches that risk commits which do not build. The time to separate them is before they are written, not after. Pull requests should explain behavior changes, list verification commands, link relevant issues, and include screenshots or recordings for UI or wallpaper changes.

## Deliberate choices

Everything here is a decision, not an accident. Each says what it costs as well as what it buys, because the cost is usually what tempts someone into "fixing" it.

- **Centre of rotation anywhere on the screen** (1.0.6). The obvious design puts the artwork's middle in the centre of the screen and spins it there. Paperouette lets that point be placed anywhere on the glass: the artwork shifts so its middle lands there, and the scene turns around it. The cost is framing, because the corner diagonally opposite is then further from the centre and sweeps a wider circle — bounded, though, at exactly twice the reach of the middle. On a tall phone that is 17% zoom in the middle, 67% a quarter of the way up, and 134% in a corner. The no-edges guarantee holds at every position, so do not "fix" a tight crop by letting an edge show; the Settings pad states the surviving fraction so the cost is visible while choosing.
- The centre of rotation is a single global setting, not per design or per remix. It is a fraction of whichever surface is rendering. The app's stage is the whole window in every layout, so the side panel overlays it and disappears while Look is open; centre placement can therefore reach the same full native surface the renderer uses. The fractions are carried unchanged between portrait and landscape, while `SceneCoverage` reframes for each shape.
- **A live-first interface** (1.0.8). A wallpaper app is usually a storefront: a small preview above a grid of thumbnails, with locked wallpapers and tiers to sell. Paperouette sells nothing and bundles the whole catalogue, so that shape earns nothing. The renderer fills the screen permanently and everything else floats over it — a sheet at rest showing the current piece and its variants, pulled up for the collection, with the filters and the centre of rotation tuned against the full-size artwork rather than on a settings page.
- **Every surface is rendered in its native orientation.** `MainActivity` follows the user's orientation preference with `fullUser`; it does not rotate portrait coordinates or keep a second centre for landscape. The wide layout leaves `LiveStage` full-window and overlays its 380 dp side panel, so showing controls or entering Play never changes the viewport or the crop. The wallpaper engine takes the surface its host supplies and cannot lock that host's orientation: a portrait-only launcher still receives a portrait wallpaper, making a landscape activity an accurate preview of a landscape surface but only a hypothetical one for that launcher.
- **The interface's vocabulary differs from the code's** (1.0.8). On screen a design is a **Piece**, a remix a **Variant**, the catalogue the **Collection**, and the gestures are **Flick** and **Nudge**. The Kotlin identifiers (`Design`, `Remix`, `designId`, `remixId`), the catalogue JSON and every DataStore key keep the older names, so no saved state has ever had to move for a wording change. Do not "fix" the mismatch by renaming the code to match the labels.
- **The artwork gives way to the app drawer** (1.0.19). `WallpaperService.Engine.onZoomChanged` was the one system hook the engine ignored. The launcher drives it from 0 on the home screen to 1 at the app drawer or recents; the scene closes in by `SceneCoverage.ZOOM_DEPTH` and dims by `SceneRenderer.ZOOM_DIM_DEPTH`, so whatever is drawn over it reads. It arrives through `MotionController.setLauncherZoom`, beside the launcher's pan, rather than through `RenderFrameState`: the window manager delivers these as fast as it animates, and a render state pushed per callback posts a frame each time, outrunning `FramePacer` while the surface is still asking the display for 30. Held in the controller, the next frame reads the latest value and a moving zoom counts as motion, so the pacer runs at 60 while it lasts. Only ever inwards, which is why it needs no refitting — reach is linear in the window's span, so scaling the span down scales the reach down and leaves the no-edges guarantee with room to spare (`SceneCoverageTest.aZoomedWindowNeverLeavesTheImageEither`). Zoom is deliberately not part of `FilterState`: the filters are what the wallpaper reports its colours through, and this is a transient the launcher is holding open. The app cannot show it, there being no launcher behind its own stage, so `launcherZoomEnabled` is a plain toggle rather than a fader — a control for something you cannot watch is worse than a choice made once.
- **The wallpaper changes itself, late rather than exactly** (1.5.0). `PaperouetteSettings.randomChangeHours` draws a variant every N hours, 0 being never. There is no alarm: an exact one needs a manifest `<receiver>`, and `package_release.py` asserts the release APK declares none — the app has an activity and a service and nothing else, and that is worth more than firing on the hour. So the check rides the hook that already runs `selectForDarkMode`, every time the wallpaper comes into view, plus a minute's tick while it is being looked at so a phone left on the home screen does not have to wait for the screen to go off. The cost is stated plainly in the panel: the new artwork arrives the next time the home screen comes up. The interval is measured from `selection_changed_at`, the last change **by any means**, so choosing a variant by hand gives it the whole interval rather than the remainder of someone else's — and setting the interval stamps it too, or turning on "every 24 hours" beside a week-old selection would spend the whole day at once. `shuffleScope` selects the whole collection, favourites or the current piece for both the button and timed changes; theme-matching is preferred within that pool, the current variant is removed, and an empty result stays put without spending the timer. Manual draws remain remembered picks while timed draws do not. It is a draw rather than a walk, because `nextRemix` and `nextDesign` already walk and a wallpaper that arrives somewhere unexpected is the point.
- **Speed** (1.0.19). `PaperouetteSettings.animationSpeed` runs the scene's catalogued animation from still (0×) to 3×. It scales `AnimationClock`'s accumulation rather than `LayerTransform`'s rotation, which keeps the timeline monotonic, so every layer stays registered with every other and the catalogued periods still divide it evenly; the user's own spin is untouched, and `MotionMath.SPIN_WRAP_TURNS` still governs that. At 0× the host stops asking for frames entirely — touch and the sensors request their own, so it comes straight back — which is the setting's real argument: a still wallpaper that still answers the hand and costs nothing idle. That is also why `EglRenderHost.update` rebases the clock on a speed change as well as on a pause: held still, the last tick can be minutes old, and resuming without rebasing hands all of it to the timeline at once and jumps the artwork. It lives in the Look panel beside Mirror and Reverse for the reason Reverse does — all three shape how the scene runs and all three want the live stage to judge against — and not in Behaviour, where **Drift** already means how long *your* push coasts. On a landscape phone this pushes Mirror and Reverse below the fold of the Filters tab; the panel is built to scroll for exactly that, and Reverse was already below it.
- **The wallpaper reports its own brightness** (1.0.18). `onComputeColors` reports the artwork's measured tone as `primary`, and states `HINT_SUPPORTS_DARK_TEXT` outright rather than leaving it to be inferred. The catalogue's `vibrantColor` is a scene's most *characteristic* colour, not its most common one, so a piece that is nearly all black advertised a bright yellow and the system painted black status-bar icons onto black — half the catalogue disagreed with its own artwork about light versus dark. `render/SceneTone` measures the real tone from the bundled thumb, cached per remix. **Both** halves matter, because readers differ: the lock screen goes by the hints, while Smart Launcher goes by `primary` and was still picking black-on-black after only the hints were fixed. `WallpaperColors.fromBitmap` returns the most populous colour first, so primary-as-dominant is what every reader expects; the accent is reported one place down. The crossover is a relative luminance of 0.179, where black text and white text have equal WCAG contrast. Filters apply, so a fully dimmed wallpaper always asks for light icons.
- **Reverse** (1.0.16). `PaperouetteSettings.rotationReversed` runs each layer's catalogued rotation backwards. It reverses the scene's **own animation**, and a **nudge** with it. The user's spin keeps its sign in `LayerTransform.totalRotationRadians`, so a flick or a drag still pushes the artwork the way the hand went — but a tap is the one input with no direction of its own to keep, and taking the fixed sign meant a nudge went the same way round with Reverse on as with it off. Since nudging is how anyone checks the setting, that read as Reverse being broken outright. `MotionController` applies the sign at the tap instead, and `aNudgeFollowsReverse` holds it there. Mirror is deliberately not consulted: it reflects the mapping, so it already turns the animation and the spin together, and correcting for it at the tap would only set the two against each other. It pairs with Mirror rather than living with the sensors, since between them they cover all four ways round a spiral can run and both want the live stage to judge against. Safe by construction for the same reason as Mirror: framing depends on the angle not at all, only on distance from the artwork's middle.
- **Mirror** (1.0.11). `PaperouetteSettings.mirrored` reflects the artwork left to right, which turns a spiral's arms — and its apparent rotation — the other way. The shader applies it as `uMirror` on the screen-to-scene mapping, reflecting about the **pivot** rather than the middle of the glass, so flipping does not also move the point the scene turns about. It is safe by construction: reflection preserves `|offset|`, and `SceneCoverage` frames by that distance from the artwork's middle alone, so the no-edges guarantee is untouched. `SceneRendererTest` checks both halves of that — the mirrored frame is the reflection of the plain one, and a mirrored off-centre scene still keeps its edges out of view.
- **Play** (1.0.9). Pushing the sheet off the bottom, or the button on the stage, leaves nothing but the artwork with the system bars hidden — the wallpaper as a thing to play with rather than to configure. Back is the way out.
- **The chrome is always dark** (1.0.8), whatever the system theme is, because light panels over full-screen artwork are not legible at any surface tone. `automaticDarkVariants` still follows the system theme to choose which *artwork* is shown; that is a separate thing and unchanged.
- The framing generalisation is exactly identity at the default centre, which is why the renderer's SSIM baselines did not move when it landed. If they ever move, the centred case has been altered and that is a bug.
- **Resolved-colour artwork over masks and ramps.** The earlier catalogue was greyscale masks coloured by ramps, which let twelve variants share one set of images and kept the whole thing at 23 MiB. The current renderers — reaction-diffusion, attractor densities, lit planets, glossy ribbons — produce colour relationships no single ramp lookup can express, so the catalogue now ships each colour variant's pixels resolved and costs 113 MiB and a texture cache with nothing to share between colour variants. That is the price of the artwork being worth looking at, and it was paid knowingly; do not "fix" it by trying to force these designs back through ramps. The four-operation `polar`/`phase`/`shape`/`ramp` vocabulary and its GLSL-transliteration ambition went with the old catalogue; the renderer's ramp path stays, unused, because the schema still admits it.

- **Artwork is separable from the app** (1.4.0). The bundled collection is what the build generated; the collection is what the user is looking at, and those stopped being the same thing. Importing takes a folder or a zip from the phone and adds it. The cost is that every invariant which used to hold by construction — counts, id uniqueness, square artwork, a scaler that wraps — now has to be *checked* on input, because a pack is a file people hand around. So `BundledCatalogRepository` keeps its exact counts and applies them to the bundled catalogue alone, and `ImportedCatalog` re-applies the rules that matter to anything imported.
- **Imported artwork is copied, not referenced** (1.4.0). A persisted `Uri` would save the duplicate — 180 MiB for a full pack — and would break the moment the user moved, renamed or deleted the folder, on a wallpaper that has to draw every frame. The grant is taken for the length of the copy and released when the source closes, so the app holds no standing access to anyone's storage.
- **Imported ids are namespaced** (1.4.0). Every imported id is `import:<importId>:<sourceId>`, and no bundled id contains a colon (`CatalogSchemaTest.noBundledIdCarriesTheImportSeparator`). Not a precaution: this catalogue kept all fourteen `spinner_*` design ids and all 208 of their remix ids from the artwork these packs are made of, so an unprefixed import would shadow every one of them. The `importId` is content-derived, so re-importing the same thing is recognised rather than copied twice, and favourites survive a remove-and-re-import.
- **Imported pictures are cropped square** (1.4.0). The layer shader turns the scene in *normalised* coordinates, so the rotation is orthogonal only when the artwork is square; on anything else it is a shear, and the picture stretches as it turns. `SceneCoverage`'s no-edges guarantee is stated in the same normalised units and so does not catch it. Cropping is what buys an imported photo the same spin, flick and nudge everything else has — and the importer clears the `rotation` of any *pack* layer that arrives non-square rather than shearing it. It also bounds the master edge: `SceneRenderer.sampleSizeFor` stops halving while the result is still larger than the viewport, so an 8000-pixel photograph would arrive whole and fail `GL_MAX_TEXTURE_SIZE` on a 4096 device, which stops the wallpaper drawing at all.
- **An imported palette is lifted before it is used** (1.4.0). `ArtworkColorScheme.legibleSeed` is the Kotlin authority for what `tools/paperouette_palette.legible_seed` does for the generator: every bundled variant arrives pre-cleared, which is why `ArtworkColorSchemeTest` passes over the whole catalogue. Artwork the user imports has had no such pass, so it gets one here. Two traps it exists for: a saturated blue clears the near-black *background* at a lightness that then fails the container surfaces chips actually sit on, and a greyscale photograph with no accent at all would seed from its loading colour — whose hue the colour maths reports as 0 and whose saturation it then floors, dressing the whole interface in red. `ArtworkPaletteTest` holds both over a few hundred generated images.
  - **Known drift:** `tools/paperouette_palette.py` says it is kept in step with `ArtworkColorScheme.kt` and no longer is — `MIN_ACCENT_SATURATION` is 0.32 against Kotlin's 0.42, `TONE_STEP` 0.04 against 0.02, `TONE_STEPS` 12 against 50. Kotlin remains the authority and the runtime is correct; the generator is merely lifting to a slightly different line. Reconciling them changes what the generator emits and so means regenerating the catalogue, which is why it was left alone here.

## Security & Offline Requirements

Never commit `paperouette-release.jks`, `keystore.properties`, credentials, or any prebuilt APK. Do not add network permissions or runtime HTTP dependencies; the app must work fully offline. Importing does not change that: it reads local files through the system picker, declares no permission, and adds no component — `package_release.py` asserts empty `receiver` and `provider` sets, which is why the folder walk uses `DocumentsContract` directly rather than `androidx.documentfile`. Never commit artwork a user imported, or a pack built from artwork this repository does not license — the remote is public, so that material stays outside the working tree entirely. Never commit generated artwork either; it is a build product and the ignore rules say so. Preserve catalogue checksums, package identity `dev.paperouette.wallpaper`, and API 37-only support.

Because those files are ignored, **a clone is not a full copy of this project**. Publishing an upgrade needs the original signing key, which is kept outside the repository and held by CI as repository secrets for tagged releases; lose it and Android refuses to update every installed copy. Where this machine keeps its copy is in `AGENTS.local.md`. The artwork needs no such care: it is generated, and `uv run tools/generate_catalog.py` rebuilds it from `tools/catalog/`.
